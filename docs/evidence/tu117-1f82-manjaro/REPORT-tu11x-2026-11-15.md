## OS-side finding (the new datum)

The 580.178.04 GSP-RM driver **fails to initialize the unlocked TU117**:

```
NVRM: GPU 0000:01:00.0: RmInitAdapter failed! (0x62:0x40:2674)   [initial, repeats]
NVRM: GPU 0000:01:00.0: RmInitAdapter failed! (0x22:0x56:897)    [later retries]
[nvidia-drm] Failed to allocate NvKmsKapiDevice
```

- GPU present on PCI (10de:1f82 rev a1), modules loaded, no nouveau fallback.
- nvidia-smi: "No devices were found"; kwin/Xwayland/Sunshine did not start.
- Contrast: on Nov 3 the LOCKED handoff (0x31 failure, FLR'd) was accepted by
  the same driver in the same power-cycle pattern. Upstream's RTX-20 "fully
  compatible" records are all tu10x dies, where the identical success-tail
  (FEAT gate open at handoff, FLR skipped) is field-proven to hand off to a
  working driver. So the datum is: **on TU117 + 580.178.04, the unlock-green
  handoff state itself is what the driver rejects** - candidates from the
  thread's own toolbox: the `\tx-relock.txt` legacy-relock knob (new default
  since 2026-11-08 is gate-open handoff), a tu11x-specific GSP expectation,
  or WPR2 state at handoff (hi=0x0 with lo=0x00f78000 here). NOT tested -
  any of those is a new owner-gated decision.
- Bench A/B could not run (no driver). Card has no tensor cores anyway;
  the family-coverage value stands regardless.

## WOL post-mortem (constraint: no further power cycles - box unreachable when off)

- OS side is correct AND persistent: after the cold boot `Wake-on: g` was
  re-applied automatically by `99-enp2s0-wakeonlan.link` (udev applies .link
  files; systemd-networkd disabled is fine). `ethtool` installed.
- NIC hardware chain supports wake-from-off: RTL8168H, `Supports Wake-on:
  pumbg`, PCIe PME `D0+,D1+,D2+,D3hot+,D3cold+`.
- Platform reality: **HP Slim Desktop 290-p0xxx** (the ASUSTeK id in the
  Nov 3 report is the GPU card's subsystem, not the mainboard). HP consumer
  BIOSes commonly gate Wake-on-LAN behind `Advanced > Built-In Device
  Options > Wake on LAN` and kill standby power via ErP/Deep-Sleep; with the
  PSU switch off the NIC is unpowered and no packet can wake it by
  definition. The failed wake is consistent with BIOS gating, not with the
  OS config.
- Definitive test for the next physical-presence session (no agent action
  needed): `sudo poweroff` (PSU stays ON) -> observe NIC link LED stays lit
  -> magic packet `etherwake f4:39:09:**:**:**` from the LAN. If dead:
  BIOS `Wake on LAN`=enable, `ErP`/`Deep Sleep`=disable; retest.
  Consider `After Power Loss -> Power On` + smart plug if remote power-on
  after PSU events matters.
- Until verified, treat every S5/PSU event on this box as requiring hands.
